# Python 架构优先开发

## 核心要求

严格按“架构设计 → 函数契约 → 完整骨架 → 逐个实现 → 验证与交付”的顺序开发。先让人看懂系统如何工作，再填充实现细节。不能先写一大段业务代码，最后补架构说明。

把易读、易维护、易修改作为设计标准。架构规模匹配任务规模：小脚本可以只有一个文件和几个职责清晰的函数；项目按实际责任划分模块，不为了显得专业而增加类、继承、插件或设计模式。

默认完成所有阶段，无需在阶段之间等待用户确认。只有影响正确性的关键需求缺失时才澄清；合理假设应说明。用户明确只要求设计或骨架时，按其要求交付。

## 1. 先设计架构

修改现有项目时，先阅读相关入口、模块、调用关系及项目约定，保留合理的现有结构，只设计本次变更涉及的范围。小修复也先说明受影响的函数和数据流，不要求重建整个项目。

在实现前，用简明文字说明：

- 目标、输入、输出和任务边界。
- 入口、模块或函数各自承担的责任，以及依赖方向。
- 从输入到最终输出的完整数据流，包括必要的失败路径。
- 配置、外部依赖和副作用发生的位置。

留下与规模相符、可供检查的设计记录：小脚本写在文件头部的模块 docstring；多模块项目使用现有设计文档，或在有维护价值时创建简短的 `ARCHITECTURE.md`。记录实际设计和关键取舍，不写空泛的架构术语。

尽量将输入输出、核心业务计算和流程编排分开；使核心逻辑能独立调用和验证。让配置和依赖通过参数传入，避免隐藏的全局状态和循环依赖。

## 2. 先定义功能函数与输入输出

根据数据流列出完成任务所需的函数，再编写函数签名、类型标注和 docstring，然后才实现函数体。每个函数负责一件可清楚命名的事；主流程只负责编排。

函数契约写在紧邻函数的 docstring 中，作为输入输出注释，不能只放在聊天或设计文档里。至少写清：

- **作用**：函数完成的具体工作。
- **输入**：各参数的含义、类型及必要的约束；涉及数组、单位、路径或格式时注明形状、单位和格式。
- **输出**：返回值的含义、类型及结构；无返回值时说明 `None` 和实际产生的结果。
- **异常与副作用**：适用时说明失败条件、抛出的异常，以及文件写入、网络请求或原地修改等行为。

返回结构应稳定、明确。不要用含糊的字典、位置难以辨认的长元组或同一函数的多种不相关返回类型隐藏契约。复杂数据结构按需要使用类型别名、`TypedDict` 或 `dataclass`，简单数据直接使用内置类型。

## 3. 先搭完整骨架，把功能串起来

先在实际代码文件中建立入口、必要的模块、函数签名和契约，并串联完整的目标流程。调用关系必须一致，参数和返回值能够衔接；不能只有互不相连的函数清单。

未实现函数用 `raise NotImplementedError("说明待实现的功能")` 明确标识。此时可以检查语法、导入和接口衔接，但不能声称端到端业务已经可运行。不要用 `pass`、伪造结果或默认成功悄悄掩盖缺失功能。

独立脚本通常使用 `main()` 和 `if __name__ == "__main__":`；库代码遵循现有入口约定，避免导入时执行业务、访问网络或写文件。

函数契约和骨架示例：

```python
def load_records(source: Path) -> list[Record]:
    """读取并校验输入记录。

    Args:
        source: UTF-8 CSV 文件路径，必须包含 id 和 value 列。
    Returns:
        校验通过的记录列表，顺序与输入一致；空文件返回空列表。
    Raises:
        FileNotFoundError: 输入文件不存在。
        ValueError: 必需列缺失或记录格式无效。
    Side Effects:
        读取文件，不修改输入文件。
    """
    raise NotImplementedError("读取并校验 CSV 记录")


def main() -> None:
    """输入：命令行配置；输出：None；副作用：读取输入并写入处理结果。"""
    config = parse_config()
    records = load_records(config.source)
    result = transform_records(records)
    save_result(result, config.destination)
```

示例仅展示契约和编排方式；实际骨架必须定义所需类型、导入及全部被调用函数。

## 4. 逐个补全实现

骨架完整后，按依赖关系逐个实现函数，优先完成能独立验证的基础逻辑，再完成外部输入输出和编排。每次实现后检查它是否满足既定契约；发现契约需要调整时，同步更新调用方、注释和设计记录。

保持以下维护约束：

- 使用能表达业务含义的名称和直接的控制流，减少深层嵌套、重复逻辑和过长函数。
- 注释解释意图、约束和关键取舍，不逐行复述代码；契约随代码一起更新。
- 配置集中表达，避免散落的魔法数字、硬编码路径和隐式环境依赖。
- 在合适边界处理异常，提供能定位问题的信息；不静默吞错，不把失败伪装成空结果或成功。
- 优先使用标准库和已有依赖；引入新依赖或抽象时说明它解决的实际问题。

## 5. 验证与交付

验证完整流程是否得到预期输出，并按风险检查重要边界与失败路径。核心逻辑应能独立验证；测试用于确认行为和契约，不为每个小改动机械增加测试。

交付完整实现前检查：

- 目标功能已沿主流程连通，输入输出契约与实现一致。
- 本次目标功能没有遗留骨架占位、伪造结果或未实现分支。
- 验证没有不必要地触发真实外部副作用；验证范围和未能验证的部分说明清楚。
- 后续维护者能从入口、设计记录和函数注释理解流程，并定位修改点。

最终简述架构、主要入口、如何运行和验证结果。若用户只要求骨架，明确标注哪些函数待实现，以及当前能进行哪些检查。
